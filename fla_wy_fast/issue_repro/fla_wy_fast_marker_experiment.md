# fla_wy_fast 标记值实验（重建版）——散列地址重写 bug 的复现尝试

> 日期：2026-11-13 · 环境：远程 910B3（DevEnvC_DCbyi_npu，CANN 9.2.0，repo `463c234c`）
> 脚本：本目录 `fla_wy_fast_marker_scatter_exp.py`（单臂） / `fla_wy_fast_marker_scatter_v2.py`（三臂）
> 背景：开发期对"散列地址重写"（伞形缺陷第 3 条，未提交）做过一次性标记值实验（结论见
> debug_log Attempt 1：cid=8 的数据落 bb=1 而非 bh=1），探针脚本未归档。本轮按原方法论重建
> 独立版，兼作该缺陷的最小复现尝试。

## 实验方法（标记值三原则）

1. **值即身份**：不搬真实梯度，改搬 `marker = cid * 64 + i`（block 编号 × 64 + 行内下标），
   读回任何数都能反解出它本来来自哪个 block 的哪一行；
2. **精度无损**：float32 对 ≤2²⁴ 的整数精确表示——比较零误差，对不上只能是地址错；
3. **落点-来源对照**：期望由"位置"正推（位置 → 该是哪个 marker），观察由"数值"反解
   （marker → 本该去哪），两者一对即现错乱路径。

kernel 结构：GRID 个 block，每块把计算出的标记跨步散列至 `dbeta[bb, s0:s0+64, bh]`
（目标元素间 stride=H）——即 bug A 的案发模式（现算源 + 跨步散列，无 GM 中转）。

## 三臂结果

| 臂 | 源类型 | 结果 |
|---|---|---|
| ARM 1 | 现算（`(m+m)*0.5` 运行时算术产出） | **1023/1024 错** |
| ARM 2（对照） | GM 载入的 `[64]` | **1023/1024 也错** |
| ARM 3（对照） | GM 载入的 `[64,1]`（真实算子里能跑通的 PB 模式形状） | 960/1024 错（仅 1 个 block 正确） |

样例错乱特征：`(0,1,0)` 读到 **0.5——是 `half` 缓冲的内容**（散列连数据源都取错了）；
`(0,0,1..3)` 全是 marker 0（一个值错落多处）；全程**零报错**。

## 结论

1. **bug A 最小复现未达成**：对照组（载入源）同样失败，无法把失败归因到"现算源"这一
   特性上。跨步散列（→ `[B,S,H]` 中维切片）在最小形态下**两种源都静默损坏**（疑与
   debug_log 记录的"子 32B 粒度 + dstStride≠0 MTE 不可靠"同族）。真实算子里"载入源 +
   [64,1] + PB 模式"能跑通，说明可工作路径依赖完整 kernel 上下文——这正是伞形草案
   "无法最小化"的根本原因。
2. **bug A 的唯一有效证据**仍是开发期真实算子内的标记实验；该缺陷至今未提交（伞形第 3 条）。
3. **方法示范有效**：重建版当场抓出实验者自己的 `out_idx` 索引错误（加参数后未改输出
   索引 → 返回张量形状断言立刻暴露）——meta 证明"值对不上位置即有错"的检查威力。
4. **方法论闭环**（#1924/#1925 教训自用）：对照组必须独立通过才具归因效力；一切比较
   前断言形状。

## 顺带发现（记案不提）

最小形态下"向 `[B,S,H]` 中维切片的跨步散列，两种源均静默损坏"本身可能值得独立报告；
但缺"连续目的地址"对照臂、归因未洗干净，先记录，不提 issue。
